Record linkage is a key step in enabling analysis of population-level trends and patterns. For example, to understand patients’ interactions with the health system it is necessary to link together datasets from the various services that they iteract with.

We have two tables and wish to find a mapping of the rows from one to the other. The problem is complicated due to differences in the way that two entities are recorded, for example via spelling errors, differences in notation and missing information.

If there was a unique identifier for each table we could do a left join, but usually we don’t have this. Instead we need to establish a mapping rule based on the information available in the data.

1. Brute force string similarity

Let’s start with one approach: comparing all pairs of rows using a string similarity function. This is a function that assigns a score to each pair, with high scores indicating a more likely match.

Jaccard similarity, Levenshtein distance, cosine similarity

We can see that the scores correspond to roughly what we expect…

The problem of course is that comparing all possible pairs of records does not scale: With \(N\) records in one table and \(M\) in another, \(NM\) comparisons are needed. In Australia, where there are over 15 million street addresses, this simply isn’t feasible.

Instead we reduce our search space by dividing the tables into blocks each containing similar sets of strings.

2. Blocking

Each block is indexed by a blocking key. For example, the name of the suburb, assuming this is available, makes a sensible key, and each block then consists of addresses in the same suburb.

However, records themselves are often not sufficiently neatly structured for such a key to be readily extracted. Instead we use the data itself to construct this.

This is the approach taken in the paper Record linkage in parallel databases using probabilistic signatures.

The idea is to split each string into substrings and count the frequenct with which each substring appears across the entire set of records. Those that are relatively infrequent make suitable signatures as they identify with high specificity the records associated with them. In other words, they make suitable blocking keys.

2.1. Inverted indexes

Let’s create the inverted index table. We split each string into phrases and for each phrase group by addresses that belong to it.

create table phrases as (
    select str_split(address, ' ') phrase from addresses
);

3.3. Implementation

Now that we understand some of the theory and algorithms, let’s implement them. Some desirable characteristics of a good implementation include:

  • Ease of installation: most data scientists are lazy when it comes to deciding which software to use, so the fewer steps it takes to install a package, the better
  • Clear documentation: simple code examples to demonstrate the software makes a package much more appealing.
  • Using well-tested tools ensure that algorithm implementations will be more performant and have fewer errors

For these reasons an obvious choice is DuckDB. It’s an open source tool based on SQL with a Python API. Unlike other SQL implementations such as Postgres is has the advantage of not requiring a user to create a SQL server instance, in order word, all the data is stored directly on a file.

5. Reference datasets

5.1. Address databases

Building a geocoder depends on having a good quality reference dataset, i.e., a complete set of clean, standardised street addresses, with corresponding latitude and longitude values.

The availability of such datasets varies widely between countries. In Australia, the Geocoded National Address File is a quarterly-updated, free and publicly available reference dataset covering the entire country. In the UK, in comparison, such data sources are ownly available commerically.
